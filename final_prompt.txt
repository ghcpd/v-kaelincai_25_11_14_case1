Enhanced Course Playback Experience

Title
Evaluation of Codex-mini, Haiku4.5, S560,Codex and S435 on Feature & improvement — Enhancement: Enhanced Course Playback Experience
________________________________________
Description
This experiment evaluates AI models’ ability to design, implement and verify a set of playback UX and performance enhancements for a video course player. The canonical problems to address are: lack of resume-from-last-position, no playback speed controls, no auto-skip for learned segments, slow loading and resolution switching, and poor synchronization between notes and playback. Project A reproduces the baseline behavior (current player). Project B implements the enhancements: progress memory & auto-resume, adjustable playback speed (0.75×–2×), auto-skip learned segments, lazy/adaptive resolution loading and improved buffering, and time-synced notes with quick-jump on hover. Validation includes functional correctness, performance under variable network conditions, and user-visible evidence (screenshots and logs).
Key evaluation criteria
• Functional correctness of all enhancement features (resume, speed control, skip, adaptive buffering, notes sync).
• Performance improvement: reduced time-to-first-frame, smoother resolution switches, fewer stalls under constrained bandwidth.
• Robustness: correct behavior under network jitter, offline/resume scenarios, and malformed note timestamps.
• Test coverage: unit tests for logic and E2E tests covering interactive flows and performance metrics.
• Reproducibility: environment scripts and one-command runs that produce machine-readable results and comparative reports.

Requirements for the AI Model Output
1.	Test Scenario & Description
o	Describe the test scenarios: resume-from-last-position, playback-speed adjustments, auto-skip learned segments, adaptive buffering and resolution switching, note timestamping and hover-to-jump behavior.
o	Provide expected input/output formats for tests (JSON). Example action: {"action":"open_course","course_id":"C101","user":"u1"}; expected player state: {"start_time_s": 125.7, "playback_rate":1.25, "current_quality":"720p", "notes_synced":[{"t":126.5,"text":"Key point"}]}.
o	Define acceptance criteria: resume accuracy within ±1s of stored time; playback-rate control applies immediately and persists per session; skip logic does not skip unlearned content; time-to-first-frame under target (e.g., ≤800ms on typical network); resolution switch completes without stalls >300ms.
2.	Test Data Generation
o	Produce at least 5 structured test cases saved to test_data.json covering:
• Normal resume: user reopens course and playback resumes near last timestamp.
• Playback speed tests: changing to 0.75×, 1.5×, 2× and verifying audio/video sync and persisted setting.
• Auto-skip learned segments: mark segments as learned and verify they are skipped when auto-skip enabled.
• Network-constrained performance: simulate low bandwidth / high latency and measure time-to-first-frame, rebuffer events, and quality switching.
• Note sync & jump: create notes with timestamps; hover or click note to jump to correct time and verify player position.
o	Each case must include initial conditions (user state, saved progress, learned segments), simulated network profile, expected intermediate states and final assertions (timing thresholds and correctness booleans).
3.	Reproducible Environment
o	Provide requirements.txt and setup.sh (or a Dockerfile) that install required Python packages (Flask/FastAPI or simple static server), a minimal frontend (HTML/JS), and testing tools (Playwright or Selenium, pytest, optionally a simple bandwidth-shaper script).
o	Include a configurable mock video server that supports simulated bandwidth/latency and multiple resolutions (e.g., serves small MP4 fragments or placeholder frames).
o	Document how to run Project A and Project B locally, how to configure network simulation parameters (bandwidth, latency, packet loss), and where artifacts are produced.
4.	Test Code
o	Provide executable Python test code that:
a. Starts the demo server and mock video server for the project under test.
b. Uses Playwright or Selenium to automate player interactions: open course, play/pause, change playback rate, toggle auto-skip, mark segments as learned, add notes, hover/click notes to jump.
c. Captures metrics: time-to-first-frame, number and duration of stalls/rebuffers, time to complete resolution switch, measured resume accuracy, and correctness of note jumps.
d. Compares outputs against expected thresholds and records pass/fail per test.
e. Produces machine-readable results files: results_pre.json and results_post.json, and human-readable logs: log_pre.txt, log_post.txt.
o	Include unit tests for the underlying logic (resume store/retrieve, skip decision, note timestamp mapping).
5.	Execution Scripts
o	Each project must include run_tests.sh to: set up environment (venv or Docker), start services, run the full test suite (unit + E2E), collect screenshots and logs, and stop services.
o	Provide a root-level run_all.sh that executes Project A then Project B tests, merges results into results/, and generates compare_report.md. One command must run the entire workflow from setup to report.
6.	Expected Output
o	For each test case produce:
• results_pre.json / results_post.json — per-test metrics and pass/fail results.
• log_pre.txt / log_post.txt — server and client traces, buffering events, and saved progress records.
• Screenshots: screenshot_pre_<testid>.png and screenshot_post_<testid>.png showing player state (e.g., playback-rate control visible, note popover, resumed position).
• Timing files: time_pre.txt, time_post.txt summarizing time-to-first-frame, average stall duration, and resolution switch time.
o	compare_report.md must include per-test comparisons (resume accuracy, playback latency, rebuff events, note-sync correctness), aggregated improvements, and visual thumbnails (links) for key screenshots.
7.	Documentation / Explanation
o	Provide README.md explaining how to set up and run each project and the full run_all.sh workflow; how to configure network simulation and thresholds; and where artifacts are saved.
o	For each test case explain its importance: e.g., resume accuracy matters for user continuity; auto-skip improves efficiency but must not skip essential content; note-sync impacts study recall.
o	Highlight pitfalls and common failure points: clock drift between player and stored timestamps, audio/video A/V drift at extreme playback rates, inconsistent chunk availability for adaptive resolution, inaccurate note timestamps from manual input, and browser-specific media behavior. Provide mitigation recommendations: server-side alignments, periodic keyframe alignment, conservative adaptive-switch heuristics, validation of note timestamps, and telemetry collection.
o	State limitations: simulated bandwidth is an approximation; real-world CDNs and codecs behavior must be validated in staging; some features (e.g., codec-level continuity at 2×) may vary by browser/platform.
